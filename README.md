# Joja Coffee — бот для колеса призов

Telegram-бот для оцифровки колеса призов Joja Coffee: колесо остаётся
физическим (бариста крутит его руками), а бот фиксирует, какой приз выпал,
выдаёт гостю уникальный код и отслеживает, когда приз погашен. По архитектуре
повторяет решение, сделанное для Evgenich — без интеграции с iiko, с ручной
сверкой в конце дня.

## Что делает бот

- `/spin` — бариста выбирает из списка, какой сектор выпал → бот генерирует
  уникальный код (например `JOJA-7F3K9A`) и текст приза для гостя.
- `/redeem КОД` — при выдаче/использовании приза бариста гасит код, чтобы
  не выдать его дважды.
- `/today` — отчёт за сегодня: сколько раз выпал каждый приз, сколько
  погашено.
- `/unredeemed` — список ещё не погашенных кодов (для контроля).

Все данные хранятся в SQLite (файл `wheel.db`), без сторонних сервисов.
Опционально каждый спин/погашение можно ещё и выгружать в Google Sheets —
см. раздел ниже.

## 9 призов (из макета колеса)

Заданы в `bot/prizes.py` — при необходимости поменять текст/призы,
редактируется только этот файл, логику менять не нужно.

## Что нужно, чтобы запустить

1. **Токен бота.** В Telegram напишите **@BotFather** → `/newbot` →
   следуйте инструкциям → получите токен вида `123456:ABC-DEF...`.
2. **Ваш Telegram ID** (и ID остальных сотрудников, которым можно
   пользоваться ботом). Узнать свой ID можно, написав боту **@userinfobot**.
3. **Аккаунт на Railway** (railway.app) — бесплатная регистрация через
   GitHub или почту, всё через браузер, терминал не нужен.

## Деплой на Railway

1. Зайдите на railway.app → **New Project** → **Deploy from GitHub repo**
   → выберите этот репозиторий.
2. В настройках проекта откройте вкладку **Variables** и добавьте:
   - `BOT_TOKEN` — токен от BotFather
   - `STAFF_IDS` — Telegram ID сотрудников через запятую (например `111111111,222222222`)
   - `ADMIN_IDS` — Telegram ID администраторов (можно совпадать с частью STAFF_IDS)
   - `LOCATIONS` — `Taganka` (или другое название точки; пока она одна)
3. Railway сам подхватит `railway.json` / `Procfile` и запустит
   `python -m bot.main`.
4. Проверьте логи в Railway — должна появиться строка
   `Joja wheel bot starting (polling)...` — значит бот запущен и слушает
   Telegram.

**Важно:** пока `STAFF_IDS` пустой, бот открыт для всех — это специально
для удобства тестирования. Обязательно заполните `STAFF_IDS` реальными ID
сотрудников перед тем, как давать боту работать с настоящими гостями.

## Выгрузка в Google Sheets

Необязательная функция: каждый `/spin` добавляет строку в таблицу, а
`/redeem` отмечает в той же строке, когда и кем погашено. Если не настроить —
бот продолжает работать как раньше, только через SQLite.

1. **Создайте таблицу** в Google Sheets (пустую, с любым названием) —
   понадобится её ID, он в ссылке: `.../spreadsheets/d/ЭТОТ_КУСОК/edit`.
2. **Создайте сервисный аккаунт** в Google Cloud Console
   (console.cloud.google.com → создать проект, если его ещё нет → в поиске
   найти **Google Sheets API** → Enable → слева **APIs & Services →
   Credentials** → **Create Credentials → Service Account** → любое имя).
3. Откройте созданный сервисный аккаунт → вкладка **Keys** → **Add Key →
   Create new key → JSON** — скачается файл с ключом.
4. **Откройте вашу таблицу → кнопка «Настройки доступа» (Share)** → добавьте
   email сервисного аккаунта (вида `что-то@ваш-проект.iam.gserviceaccount.com`,
   он есть и в скачанном JSON, и на странице аккаунта) с правом
   **Редактор (Editor)** — без этого бот не сможет писать в таблицу.
5. В Railway → **Variables** добавьте:
   - `GOOGLE_SHEET_ID` — ID таблицы из шага 1
   - `GOOGLE_SERVICE_ACCOUNT_JSON` — всё содержимое скачанного JSON-файла
     целиком, одной строкой (просто откройте файл и вставьте весь текст
     как значение переменной)
6. Нажмите **Deploy**, чтобы применить переменные. В таблице при первом же
   `/spin` появится лист `Spins` с шапкой и данными.

Если что-то настроено неверно (нет доступа, неверный ID) — бот не упадёт,
просто выгрузка не будет работать, а в логах Railway появится
предупреждение об этом.

## Сроки действия призов

У каждого приза в `bot/prizes.py` есть срок (`valid_days`) и признак
многоразового использования (`multi_use`). Срок считается от даты розыгрыша
(по времени заведения, см. `TZ_OFFSET_HOURS`, по умолчанию Москва = 3) и
включает последний день:

| Приз | Срок | Использование |
| --- | --- | --- |
| Сироп/альт. молоко до 11:00 | 7 дней | каждый день в течение недели |
| 10% на напитки после 18:00 | 7 дней | каждый день в течение недели |
| Апгрейд M→L после 19:00 | 7 дней | каждый день в течение недели |
| 10% на заказ до 11:00 | 7 дней | каждый день в течение недели |
| Скидка 10→20% за сторис, сюрприз от бариста | только день розыгрыша | один раз, сразу |
| 20% на билет + бокал, бронь стола на винный вечер | без даты окончания | один раз |

Как это работает:

- При `/spin` бот пишет срок прямо в сообщение бариста и сохраняет дату
  окончания в БД и в таблице (колонка «Действует до»).
- Недельные призы бот **не закрывает** при `/redeem`, а считает
  использования; код действует до конца срока.
- Код с истёкшим сроком бот не гасит и говорит, когда срок истёк.
- `/unredeemed` показывает сначала действующие призы (ближайший срок
  сверху), потом просроченные.
- В таблице: колонки «Осталось дней» и «Статус» (Активен / Истекает /
  Просрочен / Погашен / Без срока) считаются формулами от сегодняшней даты,
  строки подсвечиваются (просрочен — красным, истекает — жёлтым), на шапке
  включён фильтр. Лист **«Активные»** собирается сам: только действующие
  призы, ближайший срок сверху — по нему бариста ищут код через Ctrl+F.
  Строки, созданные до появления сроков, получают статус «Без срока».

Чтобы поменять срок приза, поправьте `valid_days` в `bot/prizes.py`
(`0` — только в день розыгрыша, `None` — без срока).

## Если понадобится вторая точка

Добавьте её в `LOCATIONS` (через запятую) и добавьте в `/spin` выбор
локации перед выбором приза — сейчас бот использует первую точку из списка
автоматически, чтобы не усложнять интерфейс на старте с одной точкой.

## Если появится доступ к iiko API

Сейчас бот работает полностью независимо от iiko — это осознанный выбор
(как и в Evgenich), чтобы не зависеть от того, есть ли у вашей версии iiko
доступ к API. Если окажется, что доступ есть, интеграцию можно добавить
позже отдельным шагом — текущая архитектура (SQLite + коды) для этого не
помеха, а хорошая база.
